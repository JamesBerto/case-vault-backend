# Case Vault backend

The backend implements the PDF's case, evidence, role, tag, and audit API requirements. The PDF is a documentation snapshot and is not changed by these backend updates.

## Setup

Use Python 3.12 and a MongoDB replica set (including a single-node replica set for local development). Transactions are required for metadata changes. Install dependencies with `python -m pip install -r requirements.txt`; for tests also install `requirements-dev.txt`. Configure `MONGO_URI`, `DB_NAME`, and `JWT_SECRET` in `.env` as expected by `app/core/config.py`. `CORS_ORIGINS` is an optional comma-separated list of allowed frontend origins; its default covers Vite on localhost port 5173.

On an existing database, stop API writes, back up the database, then run `python -m app.services.migration_service`. The migration checks for duplicate `(evidence_id, version_no)` and `(case_id, tag_id)` pairs before creating unique compound indexes, backfills version counters, grants tag creation to admin/analyst and tag assignment to admin/analyst/reviewer, and removes tag creation from the built-in reviewer role. It also removes deletion grants from built-in analyst/reviewer roles. It preserves custom roles and prints conflicting custom-role deletion grants for manual review. Resolve duplicates manually before rerunning; the migration never rewrites or removes conflicting records. It adds a TTL index for active sessions and is idempotent. Startup fails if any required index is absent. Fresh installations can run `python -m app.services.seed_service`, which also runs the migration. Change the bootstrap admin password immediately.

Start the API with `uvicorn app.main:app --reload`, then open `/docs`. `GET /cases` supports `status`, `case_type`, `q` (literal case-number substring), `analyst_id` (the case creator ID), and inclusive `submitted_from` / `submitted_to` calendar dates. Case timestamps are stored as naive UTC; date bounds are interpreted as UTC days. Evidence is listed by `GET /evidence/by-case/{case_id}`. Admin-only `GET /cases/deleted` and `GET /cases/deleted/{case_id}` and `GET /evidence/deleted/{evidence_id}` inspect archived metadata. Normal evidence endpoints return 404 when the evidence or parent case has been soft-deleted, even for admins.

`GET /users/me/access` returns the signed-in user's role and current permission codes for navigation. `POST /auth/logout` revokes the presented bearer token until its expiry; expired revocation records are removed by a MongoDB TTL index. Evidence uploads can also store optional description, source device, and notes fields used by the frontend.

Each account has one active login session. A second login with valid credentials returns HTTP 409 while the first session is active. A successful logout releases the slot immediately. Authenticated requests renew a three-minute server-side lease, and the frontend calls `POST /auth/heartbeat` every minute while open. If the tab closes or loses connectivity, another device can sign in once that lease expires; the old token then fails authentication even if its eight-hour JWT expiry has not passed. Browser sleep or throttling can also let the lease expire while a tab is open, in which case the user must sign in again. Changing an account's active status releases its slot, so a reactivated account must sign in again. Session records contain a SHA-256 token hash, never the raw token. The `active_sessions` collection uses the unique MongoDB `_id` per user and an `expires_at` TTL index; login also checks both JWT expiry and lease freshness directly because TTL cleanup is asynchronous. Existing active sessions without `last_seen_at` use `started_at` for the initial lease check; sessions older than three minutes must sign in again after deployment. No new database migration is required for this change. A copied bearer token can still be used elsewhere while its session is active. Account deletion is unavailable; administrators can deactivate or reactivate accounts through `PATCH /users/{user_id}`.

Passwords must contain 8–128 characters. Self-service password changes reject a local list of common passwords and obvious sequences. Only the built-in admin role may use a common password when creating an account with a temporary password; the temporary password is not automatically expired or forced to change, so the user should replace it in Password Settings. This local check is not an exhaustive breached-password screening service. New hashes use bcrypt-SHA256 so all 128 characters matter; existing bcrypt hashes still verify and are replaced with the new scheme when changed. No database migration is required.

Any authenticated user with `case:view` can remove a tag from an active case. Removal deletes only that case-tag association and records `tag_removed`; the tag remains available for other cases. Tag assignment requires `tag:assign` and is available to administrators, analysts, and reviewers. `DELETE /tags/{tag_id}` is admin-only and permanently removes a tag from the available options and all case associations in one metadata transaction. It records `tag_removed` for each affected case and `tag_deleted` for the global deletion.

PDF uploads are limited to 10 MiB (10 × 1024 × 1024 bytes) for both initial evidence and replacement versions, and are parsed for structural validity using `pypdf`; this is not malware scanning. SHA-256 verification happens on demand. GridFS does not support multi-document transactions, so file bytes are stored before metadata is committed. A definite metadata failure triggers GridFS cleanup. A process crash, failed cleanup, or uncertain commit result can still leave an orphaned file or uncertain file/metadata state and requires operator reconciliation; do not assume file and metadata are fully atomic.

`GET /evidence/{evidence_id}/versions/{version_id}/verification-status` reads the latest recorded check for an active evidence version using `evidence:view`. It returns `Not checked`, `Intact`, `Mismatch detected`, or `Check failed` with the check time and actor when available. `Intact` means the stored bytes matched the upload hash at the displayed check time. This is a historical result, not continuous monitoring; the version's `is_tamper_flagged` value remains separate and is not cleared by a later matching check. Existing audit entries supply the status, so no migration is needed.

Tests use `python -m pytest -q`. The integration test requires `TEST_MONGO_URI` pointing to a transaction-capable **test** replica set. It creates a random `cv_test_*` database and drops only that database. Never set `TEST_MONGO_URI` to production. Without this variable, the integration test is skipped, not passed.
